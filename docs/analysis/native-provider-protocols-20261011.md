# Native provider protocol checkpoint

This checkpoint implements owned Pi RPC, Codex app-server and Claude stream processes. Existing Herdr Workspace/Agents, installed CCB, user provider settings and `codex_impl` were not controlled or changed.

## Local primary sources

- Installed Pi package: `@earendil-works/pi-coding-agent 1.1.0`. Its `docs/rpc.md`, `docs/rpc-commands.md`, `docs/json.md` and `dist/modes/rpc/rpc-mode.js` define prompt dispositions, LF-framed events, session state and `agent_settled`.
- Installed Codex executable: `codex-cli 0.162.1`. Its `app-server --help` confirms stdio transport. `app-server generate-json-schema` was run into a unique temporary directory, without starting a model task. The generated InitializeParams, ThreadStart/ResumeParams, TurnStartParams, TurnCompletedNotification, ItemCompletedNotification, ThreadReadParams/Response and TurnInterruptParams schemas were inspected directly.

## Codex driver

`driver_kind: "codex_app_server"` requires `provider: "codex"` and a command argv that starts an app-server. Initialization and thread binding use ID-correlated responses. Saved non-ephemeral thread IDs resume through `thread/resume`; a different returned ID is rejected. Configured `thread_options` and `turn_options` are forwarded; the driver does not silently grant approvals.

Turn submission sets the owned thread, unique request ID and `clientUserMessageId`. Notifications arriving before the start response are bounded and buffered, then filtered against the accepted turn ID. Commentary and partial-answer messages are not final results. A matching `turn/completed` triggers `thread/read`; only the same terminal turn in the same idle thread completes the task. Final-answer text is preferred, with phase-unknown compatibility for legacy models. Foreign thread/turn events cannot release the slot. A persistent Pi Lead + native Codex protocol fixture passed automatic callback execution.

An actual installed app-server completed initialize/thread-start in a private `CODEX_HOME`, private working folder and ephemeral thread. No turn/model request was sent. This is real transport/schema evidence, not proof of real model execution.

Later model-backed Pi/Codex checks are recorded separately in [the real-model checkpoint](native-real-model-checkpoint-20261011.md).

### Codex cancellation and deadlines

Explicit API-2 cancellation and configured `timeout_s` deadlines append a Job cancellation intent and event through the native journal before provider IO. The intent fixes the reply policy and binds the running execution; duplicate requests do not send another interrupt. If the start response is delayed, the intent waits for its accepted turn ID. The owned driver then sends `turn/interrupt` with that exact thread/turn pair. The empty response is acknowledgement only, as defined in the [official App Server protocol](https://learn.chatgpt.com/docs/app-server) and the installed TurnInterruptParams/Response schemas.

Neither acknowledgement, rejection, elapsed time nor a foreign terminal event frees the slot. Completion still requires the matching terminal turn and idle-thread verification. A natural completion racing cancellation retains the provider's actual status; silent cancellation suppresses its reply. A failure after a cancellation request cannot automatically retry the task. Control acknowledgements/errors are visible in safe session metadata and the final decision.

Daemon death preserves the explicit intent; an old running execution remains fenced. This is durable intent and replay prevention, not completed running-task reconciliation. These controls were tested with owned protocol fixtures; successful real-model interruption remains a separate acceptance check.

## Codex interactive requests

The owned connection accepts command/file approvals, additional permission
requests, tool user-input questions, MCP elicitations and dynamic tool calls.
Request parameters and explicit answer shapes are checked against embedded
schemas generated by installed Codex 0.162.1; HTTP/file schema resolution is
disabled. Configured initialization capabilities are validated and forwarded;
experimental methods remain opt-in, and required lifecycle notifications cannot
be suppressed. No approval or tool execution is inferred automatically.

API-2 `provider-requests` takes `agent_name` and returns pending requests with an
opaque native handle, job/execution/runtime binding, method, params and status.
`provider-respond` requires that binding and a method-specific `result`. Only
the live owned turn accepts a response. Invalid answers, excessive permission
grants, wrong task/runtime identities, resolved prompts and cancelled tasks are
rejected before forwarding. Identical duplicate answers enqueue once; a changed
answer is rejected. A fresh native handle prevents a stale UI answer from
answering a subsequent turn that reuses a server wire ID.

Native CLI equivalents are:

```powershell
ccb-native --state-root <state-directory> pending worker
ccb-native --state-root <state-directory> respond worker <request-id> <answer.json>
```

The answer file contains the provider response object, for example
`{"decision":"decline"}` for a command approval. UTF-8 BOM files are accepted;
reads are bounded. CLI receipts do not echo answers. Native durable audit and
session summaries keep identifiers/statuses without storing interactive answer
payloads. Ordinary provider final replies retain their existing persistence
semantics. The authenticated pending-query response exposes the original prompt
to its caller; the bridge does not open MCP URLs or execute dynamic tools.

`response_queued` and `serverRequest/resolved` do not complete the task or release
FIFO. Only the existing matching turn/idle verification does that. Pending UI
state retires on resolution, cancellation or task termination. Provider-owned
prompts/answers are not replayed into a new process after daemon death; unknown
old running executions still require reconciliation. Session metadata is not
published until a real thread identity is confirmed.

Owned fixtures cover explicit decisions/input, invalid response rejection,
binding fences, duplicate and stale replies, startup ordering, restart/cancel
cleanup, and Pi Lead automatic continuation after Worker interaction. They do
not prove successful real-model approval handling or a graphical approval UI.

## Pi restore and cancellation

When a saved Pi binding has a session file, native startup passes that exact file via `--session` and checks the returned session ID. A missing file or different ID fails closed. A `--no-session` binding has no durable history to resume.

The public native cancel operation queues Pi `abort`; its response reports cancellation requested, not task completion. The driver waits for the anchored run's `agent_settled` and a correlated idle state. Silent-cancel intent is carried into the terminal decision and prevents reply synthesis. Pi deadlines request abort and similarly wait for provider evidence; elapsed time alone never releases the slot.

## Claude control and terminal correlation

Native explicit cancellation and `timeout_s` deadlines persist Job/Event intent
before sending an owned `control_request` with subtype `interrupt`. Request IDs
bind the process generation and user message UUID. Empty success acknowledgements,
errors, unknown UUIDs and elapsed time do not release FIFO. If `still_queued`
contains the current UUID, the driver requests its targeted
`cancel_async_message`. A correlated positive queue-removal receipt (or that UUID
in the interrupt's `cancelled` list) is exact evidence that this queued input will
not execute; it can finish without a user replay that never happened.

Normal results retain session/parent/echo fences and validate `user_message_uuid`
or `user_message_uuids` when present. After queue cancellation, that attribution
is mandatory and remains so across clean restarts, preventing a late result of
the retired input from finishing the next task. Older producers without those
fields retain ordinary legacy result handling before queue cancellation; they
cannot provide this stronger post-cancellation attribution. Unsupported or
unattributed frames are not substituted with inferred completion.

`terminal_reason` values `aborted_streaming` and `aborted_tools` identify a
cancelled turn. A natural completion racing an interrupt keeps its actual
provider outcome. Error-subtype `errors` arrays enter failure classification;
cancellation intent prevents automatic retry and preserves silent reply policy.
An exit fallback waits for both confirmed process exit and stdout EOF, so a valid
result behind the bounded output backlog is not discarded. An exited process
does not make a new task ready or shut down the daemon.

Primary protocol source: the official `@anthropic-ai/claude-agent-sdk` 0.3.296
`sdk.d.ts`, matching installed Claude Code 2.1.296 according to
[Anthropic's changelog](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md).
The pinned type source is
https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.296/sdk.d.ts.
It defines the control envelope, interrupt receipt, targeted cancellation,
result user UUIDs and terminal reasons; the driver does not borrow Managed
Agents' separate HTTP event protocol.

An owned installed CLI in a new private home/workspace accepted initialize and
idle interrupt controls; its reported version was 2.1.296. Another private
probe accepted idle interrupt without initialization. Both returned empty
`still_queued`/`cancelled` lists. Neither probe sent a user prompt or invoked a
model, and user environment/login/Workspace were unchanged. Successful actual
model interruption is still unverified; owned fixtures cover running/queued
cancellation, missing or late results, deadlines, restart fences and EOF backlog.
